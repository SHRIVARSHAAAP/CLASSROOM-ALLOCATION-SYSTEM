# 2. Product, roles and golden rules
Five portals, each with its own login option and dashboard, on one common secure authentication system:
- Admin: manages classrooms, timetable, cancellations, rescheduling, permissions, issues, club bookings, attendance mapping, maps.
- Rep (class representative): reports cancellations and classroom issues, requests permission to change a classroom, then changes it once if approved.
- Club Member: finds free rooms, requests bookings, generates the HOD letter PDF, uploads the signed letter.
- Faculty: views teaching schedule, locations and updates; MARKS ATTENDANCE for their own sessions (the only write permission faculty have).
- Student: views timetable, room changes, attendance, notifications, classroom finder. Cannot edit allocations or book rooms unless the account also has club_member permission.

Golden rules:
1. The published fixed (recurring) timetable is NEVER overwritten by one-time changes. Cancellations, makeup classes and temporary room changes are stored as separate occurrence overrides layered on top.
2. ONE availability source (lib/availability.ts). Regular sessions (after overrides), makeup classes, temporary room changes, approved club bookings and maintenance blocks are all checked through it, so double-booking is impossible. Touching time boundaries are not overlaps.
3. Hard validation (lib/allocation/validator.ts, pure TypeScript, no DB calls): capacity sufficient; required facilities present AND working in the needed quantity (projector, computers, smart board, lab equipment, AC...); room type matches; room active and not in maintenance; no other booking at that time; faculty free; student section free; approved club reservations respected; rep permission valid for that exact change. Any violation means the change is invalid and must not be saved.
4. If no suitable room exists, explain exactly why and suggest alternatives (adjacent slots, rooms missing only one facility). If a class cannot be allocated at all, create an HOD consent request: the admin records the HOD's decision offline (accepted or declined, with a note). On accepted, apply the agreed compromise, notify BOTH the faculty and the reps of the section, then reschedule. On declined, keep the class waiting with the reason visible. Classes have a priority (normal or high) that affects queue order and scoring tie-breaks.
5. Every mutation writes an append-only audit log row (actor, action, entity, before, after, time) and calls notify(). Website notifications always work; WhatsApp is sent only with recipient consent and must never block the website notification.
6. Zod validation on every input. RBAC checked inside EVERY API route with a shared requireRole() helper, not only in middleware. Typed query helpers in lib/queries.ts. No secrets in the client bundle.
7. Allocation logic is pure TypeScript in lib/allocation/ so it can be unit tested and benchmarked.

# 3. Roll numbers
lib/rollNumber.ts holds an EDITABLE config mapping. Format: 2-digit year + department letter + digits (case-insensitive), e.g. 23Z... Mapping: B = Biomedical, A = Civil, Z = CSE, E = EEE, L = ECE, N = AIML, T = Textile, I = IT, R = Robotics, F = Fashion Technology, P = Production Engineering, U = Automobile. parseRollNumber(roll) returns { year, deptCode, department }. After first login show a one-time "Confirm your department" modal pre-filled from the parsed letter; the student confirms or picks another, and it is saved and used everywhere afterwards. Unknown letter means the student picks manually. Unit-test every letter, lowercase input and an invalid roll number.

# 5. Feature specification

## Admin
- Dashboard cards: total classrooms and availability, today's scheduled and cancelled classes, pending cancellation reports, pending issue reports, classes awaiting rescheduling, pending rep permission requests, pending club approvals, recent classroom changes, WhatsApp delivery status.
- Classroom management: add, edit, deactivate (never hard-delete a used room); building, floor, room number, capacity, facilities with working quantities; maintenance windows; free/occupied weekly view; search and filters.
- Fixed timetable: CSV/Excel upload with preview, column mapping, per-row validation, error report, import valid rows only; manual add/correct; conflict detection (room, faculty, section); draft vs published versions; publish the official timetable; room-wise, section-wise and faculty-wise weekly views.
- Cancellations: approve/reject reports; approved ones are marked cancelled and release the room for THAT date only; admin decides if a makeup class is required; history.
- Smart rescheduling: list classes awaiting makeup; search free dates and slots; check faculty and section availability; find suitable rooms by capacity and facilities; rank combinations with scores and a "Why this?" explanation; confirm and publish; notify rep and faculty.
- HOD consent flow as in golden rule 4.
- Rep permissions: approve with an expiry, tied to one session, single use; reject; revoke unused; view all changes reps made.
- Classroom issues: mark rooms temporarily unavailable, suggest alternative rooms, approve a classroom change, track resolution.
- Club approvals: view requests with club, event, organizer, room, date, time, reference number; open the signed HOD letter; RE-CHECK availability at approval time; approve or reject with a reason; cancel or modify approved reservations with notification.
- Reports: utilization heatmap (day x hour), cancellations and reschedules, successful vs unresolved rescheduling, room-change history, issue frequency, approved vs rejected club bookings, occupancy, attendance reports, allocation efficiency of the smart algorithm vs a baseline first-available-room algorithm (conflicts, % allocated, seat utilization, wasted seats, unused room-hours, assignments changed after an update). CSV and PDF export.

## Allocation engine (lib/allocation/)
constraints.ts, validator.ts, scoring.ts, suggest.ts, explain.ts, baseline.ts, metrics.ts. Score every valid room 0 to 100 on seat wastage (do not put 30 students in a 150-seat hall), distance from the department's building, facility fit (do not waste rare facilities), same-building continuity for the section, balanced utilization, and the section's home room as a soft preference. suggestRooms returns the top N with a "Why this room?" explanation and the top 2 rejected alternatives with reasons. Reusable <RoomSuggestionList> component with disabled rooms showing the reason.

## Rep
Dashboard (today's classes and rooms, fixed timetable, cancelled/rescheduled sessions, pending requests, notifications). Report cancellation (class, reason, status tracking). Report classroom issue (room, session, type, description, optional image to Supabase Storage with limits, status tracking). Request permission to change classroom; after approval, a Change Classroom screen showing only suitable free rooms, automatic conflict check, saving as a temporary override, permission marked used in the SAME transaction (a second use must fail), published views updated. A rep can only act on their own section.

## Club member
Dashboard; classroom finder (date, time, building, floor, minimum capacity, projector/computer, room type, other facilities) excluding rooms occupied by classes, makeups, approved club bookings or maintenance; booking form (club, organizer and department, faculty coordinator, event and purpose, date, start and end, expected participants, facilities, preferred room) validated before proceeding; formal A4 HOD permission letter PDF via pdf-lib (college and department details, club and event, organizer, room, date and time, participants, purpose, coordinator, blank signature/date/seal space) with download and print; unique booking reference with a copy button shown on the PDF, details page, admin page and notifications; upload the signed letter (PDF/JPG/PNG, size limit); status machine Draft -> Awaiting HOD Signature -> Signed Letter Submitted -> Approved/Rejected, Cancelled, with invalid transitions rejected server-side; My Bookings with re-download, tracking, cancel pending.

## Faculty
Read-only dashboard: today's classes, rooms (building, floor), upcoming sessions, cancellations and confirmed makeups, updated locations, notifications. Faculty do not report cancellations or issues. Attendance marking: today's sessions (including makeups, excluding cancelled) with a mobile-first roster grid (tap Present/Absent, menu for Late/On Duty/Excused, mark all present, search, live count), submit locks the sheet, later edits need a reason and are audit-logged, admin can unlock. Server-side rules: only the session's own faculty or admin; not for cancelled sessions; only on the session's date (configurable grace); makeups are their own sessions.

## Student
Fixed timetable from the saved department/year/section, today's classes with room, building and floor, cancelled and rescheduled classes highlighted, notifications, classroom finder ("Where is CSE-304?"). Attendance (read-only): subject-wise percentage rings, calendar heatmap, session history, warning below 75 percent (configurable) with classes needed to recover = ceil(3*total - 4*attended) for the 75 percent rule; cancelled sessions excluded from totals, makeups included. Students see only their own records.

## Attendance mapping
Auto-map students to sections from roll number + year + section; list unmapped and mismatched students for the admin; CSV/Excel mapping import with validation; elective and lab-batch mapping UI; one function lib/attendance/roster.ts resolves the roster for any session instance. Low-attendance and "not yet submitted" reports; cron reminder to faculty.

## Room mapping and allotment mapping
- Map editor (admin): place buildings on the campus canvas, upload an optional floor-plan image per floor, drag and resize room shapes linked to classrooms (snap to grid, no overlaps, inside bounds, one shape per room), draw the walking-path graph (gate, entrances, junctions, stairs, lift, room doors) and warn about unreachable rooms.
- Live map (everyone): campus view with live free-room counts, building -> floor -> floor plan with rooms coloured for the chosen date and time (free, regular class, makeup, club booking, maintenance) using patterns/icons as well as colours; hover/tap details; date picker and 08:00-18:00 scrubber; filters by facility, capacity, type; "Find free room"; search "Where is CSE-304?" drawing the shortest path from the gate (Dijkstra) with meters, minutes and floor-by-floor steps; students get "Navigate to my next class". If a building has no floor plan, auto-generate a grid layout; mobile uses a list with a bottom sheet.
- Allotment map (admin): split view with sessions to place on the left (unallocated, makeup awaiting a room, draft sessions) and the floor plan on the right. Dragging a session onto a room runs validateChange instantly (green valid, red violations list; hard violations block the drop); save as a draft timetable edit or one-time override. Allotment overlay coloured by department or section; per-room day strip; section home-room mapping; top 3 suggested rooms highlighted with "Why this room?". Path changes recompute building_distances used by scoring.
- Cinema-style room view (reuse in finders and dashboards): seat grid per room (rows x cols with a board bar), green free, red class, amber reserved/club/makeup, grey maintenance, with the time scrubber and a room detail drawer (current class, faculty contact, facilities available vs needed). Optional 3D toggle only if everything else works.

## Notifications and audit
lib/notify.ts is the only way to send notifications. Events: rep reports cancellation, issue or permission request -> admin; permission decision -> rep; cancellation confirmed -> rep and faculty; rescheduling confirmed -> rep and faculty; rep changes classroom -> admin, rep, faculty; signed letter uploaded -> admin; club decision -> club member; approved booking modified/cancelled -> club member and admin; HOD accepted -> faculty and reps; student below attendance threshold -> student. Website bell via Supabase Realtime with unread count. WhatsApp via the official Business Cloud API with consent checks, approved templates, retries, delivery tracking and a webhook (GET verify, POST status, signature check). WHATSAPP_MODE=mock|live; mock mode logs to the database and shows a message-log panel so the demo works without credentials. Document template names and texts in docs/WHATSAPP_TEMPLATES.md. Admin notifications page with delivery filters and Resend for failed. Audit log page with filters, before/after diff and CSV export.

# 5b. REAL CAMPUS MAP (supplied by the college)
The supplied map is an ILLUSTRATED ISOMETRIC (angled 3D) picture of the campus, NOT a top-down plan. Save it as public/maps/campus-map.jpg (native 912 x 624; the admin must be able to replace it with a sharper image later without losing hotspots, so store all positions normalized 0..1). Never crop, stretch or recompress it: render with object-fit: contain at its native aspect ratio so the WHOLE map is always visible. Initial hotspot anchors for every label are in data/campus_blocks.json (load it in the seed script).
Labels on the map: academic blocks A, B, C, D, E, F, G, I, J, K, M, T, Y; other buildings Industrial Labs, RMD, HED, New Admin Block, PSG IM, PSG Sarvajana School; pins Store, Restroom, Canteen, Xerox (two), PSG Parking, Quadrangle (main entrance, bottom-left, reached from Avinashi Road); roads Avinashi Road, Pioneer Mill Road, PSG Hostel Road. The blue lines drawn on the map are pedestrian walkways: use them as the starting path graph.
Requirements:
1. Hotspot overlay: an SVG layer with viewBox equal to the image pixel size, placed exactly over the image so it scales with it. Each academic block gets a clickable polygon (initially a rounded rectangle around its anchor, editable in /admin/map-editor by dragging vertices) with hover highlight and a chip showing the block letter and its live free-room count. Click -> the block's SIDE VIEW. Non-room places (canteen, xerox, restroom, store, parking, school) are info pins only; New Admin Block, RMD, HED, Industrial Labs and PSG IM can be marked as having rooms by the admin.
2. SIDE (elevation) VIEW of each block, entirely visible: floors stacked as rows (ground at the bottom), every room a cell with its number. Every block has AT LEAST 50 rooms and all of them must be on screen at once, with nothing clipped: size the cells from the room count and the container (fit width and height), compact labels (room number only) when cells are small with details on hover/tap, zoom/pan and full-screen, no horizontal page scroll. Rooms are coloured by live status for the chosen date and time (free, regular class, makeup, club booking, maintenance) with patterns/icons as well as colours; floor filter chips; facility filter dims non-matching rooms; free-room counter per floor and per block. Click a room -> detail drawer, floor plan, "Navigate".
3. Auto-layout when a floor has no custom plan: central corridor, rooms on both sides, evenly spaced, wrapping for long floors; it must work for 10 to 40 rooms per floor. Admin can switch a floor to the manual drag-and-drop editor.
4. Navigation: the main entrance anchor is "Quadrangle". Shortest path (Dijkstra) over the walkway graph from the entrance to the block, then through the block's stairs/lift to the room, showing meters, minutes and floor-by-floor steps, drawn over the campus image. If the admin has not drawn walkways yet, fall back to straight segments between block anchors.
5. Seed data: a generator script db/seed_rooms.ts creates at least 50 rooms for EACH of the 13 academic blocks (A, B, C, D, E, F, G, I, J, K, M, T, Y), default 4 floors, numbering "<block>-<floor><nn>" (A-101, A-102 ...), mixed room types, capacities 30 to 200 and facilities, a few rooms in maintenance. Provide an editable config data/block_departments.json mapping each department to its home block (placeholders; the admin will correct it) used by the allocation scoring. Real room lists replace the generated ones through the CSV import.
6. Performance: SVG with memoized room cells; moving the time scrubber updates only the rooms whose status changed; lazy-load the map; smooth with 650+ rooms in the system.
7. Known limits of the supplied image: it is a photo of a printed poster at low resolution and is cut off at the left edge (B, Store, Xerox), the right edge (M) and the bottom (PSG Hostel Road / Main Block Ground). Add an admin "Replace map image" action and show the whole image as given; do not try to re-draw the missing parts.
8. Tests: layout never overflows for 1, 10, 50 and 120 rooms per block; each room rendered exactly once; hotspot positions are correct after resizing the window and after replacing the image with a different resolution; status colouring matches availability; pathfinding with a missing walkway falls back correctly.
