Prompt 0: Project brief
Build the "Smart Campus Room Management System" for PSG College of Technology.
Stack: Next.js 15 (App Router), TypeScript, Tailwind, Supabase (Auth + Postgres +
private Storage), zod, Recharts, pdf-lib, Vitest. Five portals: Admin, Class Rep,
Club Member, Faculty, Student.
Core rules:
- The fixed weekly timetable is never edited by one-time changes. Cancellations,
  room changes, makeups and club bookings are stored as separate dated records.
- ONE shared availability module (lib/availability.ts) is used by every feature.
- Rooms are shown GREEN "Available" or RED "Not available", always with a text
  label, never colour alone.
- Theme: navy #1B3A82, text #1B2F6E, teal #0E7C7B, slate-blue #4A6A9E.
  Fonts: Poppins (login), DM Sans (app). Light/dark mode, mobile first, accessible.
- Readable, formatted code (no one-liners). Pure logic in /lib and /lib/engine.
  Add Vitest tests for logic. Never expose the service-role key to the browser.
Confirm, then wait for my next prompt.

Prompt 7: Cancellations and issues
Rep: report a cancellation (session + reason) and classroom issues (type, description,
optional image to private storage). Admin: approve or reject; approval marks only that
date's occurrence as cancelled and releases the room for that date. Then display a
"Class cancelled" card to the rep, faculty and affected students with: subject,
section, faculty, date, time, room, the REASON, who reported and approved it, and
the status. The room turns green on the map for that slot. Admin can mark rooms
unavailable, suggest alternatives and track issue resolution. Add history, audit logs
and notifications.
Prompt 8: Allocation engine and automatic reschedule suggestions
Build /lib/engine. Hard constraints: faculty free, section free, room free, capacity >=
section size, required facilities, room not in maintenance. Soft score: seat fit, same
or preferred block, walking distance between the section's neighbouring classes,
avoiding the section's heavy days, minimal gap from the original time, and avoiding
scarce-room misuse. Build a first-fit baseline and an optimized allocator.
AUTOMATIC SUGGESTIONS: when a cancellation is approved and a makeup is required,
run the engine immediately for the next 14 college days (skip holidays) using the
faculty timetable, the section timetable, club bookings, maintenance, existing makeups
and room availability. Show the top 3 ranked slots to the Admin, each with the room and
a checklist (faculty free, section free, room free, capacity fits) and a short reason.
Admin confirms one (transactional re-check against double-booking). That publishes the
makeup, notifies the rep, faculty and students, and turns that room red for the
new slot on the map. If nothing fits, explain which constraint failed. Re-allocate only
affected classes when availability changes and measure how many moved. Tests: faculty
clash, section clash, room clash, capacity, and beating the baseline.
Prompt 9: Rep permission and change classroom (with map)
Rep requests permission for one session with a reason. Admin approves with an expiry,

room free, capacity and facilities fit), save. Saving consumes the permission and
updates the published timetable. Too-small or ill-equipped rooms show red with the
reason. Log everything and notify admin, rep and faculty.

Prompt 11: Signed letter and admin approval (with map)
